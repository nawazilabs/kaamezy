# Kaamezy web frontend

Static files, no build step: `index.html` (shell, auth, merchant chat), `flows.js` + `flows.css` (health insurance and loan flows). It calls the FastAPI backend over HTTPS.

Flow: sign in / sign up (Supabase) -> Paytm-style wallet home (only the "Kaamezy Teammate" tile is live)
-> Kaamezy landing (link a business or try a sample merchant) -> assistant chat, plus "Behind the scenes"
(trace, agent desk, audit log, red-team, scorecard). On desktop it renders inside a phone frame.

- Auth: Supabase JS from a CDN, using the project's publishable (client-side) key. The login is front-end only; the FastAPI backend does not check it.
- Backend URL: defaults to the Render deployment; override with `?api=https://...` or the "API" link on the landing page (kept in localStorage).
- On `localhost` it talks to `http://localhost:8000`.
- Supabase dashboard: add the deployed URL under Auth -> URL Configuration -> Redirect URLs (needed for confirm and reset links).
- Vercel: Root Directory `web`, Framework Preset `Other`, no build command, no output directory.
- Local: `uvicorn chaukas.main:app` and `python -m http.server 8080 --directory web`.

- Health insurance and loan flows call the backend (`/api/consumer`, CONTRACTS C5b): the server's rule engine prices, the simulated lender decides, a deterministic guardrail gates every policy and loan, and every decision goes to an append-only audit log. The browser sends its Supabase token; the server checks it. If the backend is down the flows show an error (there is no offline fallback). The assistant is the backend LLM agent (`/api/consumer/assistant`), with a knowledge-base fallback.
- **Voice:** the round mic above Scan QR on the home screen records up to 20 seconds, the server turns it into text with Sarvam Saaras (nothing stored), and the text goes through the normal assistant path. "I need a loan of one lakh for twelve months, income sixty thousand" fills the loan form; "I want health insurance" opens the quote flow. Replies can be read aloud (speaker on each reply; auto-play after a spoken request) with Sarvam Bulbul in 11 languages. Voice never gives consent, OTP or approval: those stay taps. Needs `SARVAM_API_KEY` on the server and a browser that allows the microphone (https or localhost).
- **Payments (fintech):** four screens on the home screen under Payments & Money, all on simulated partners. *Payment help* lists transactions and, for a failed payment where money was debited, shows the cause, a three-step refund progress, the usual time, "Raise a dispute" and (when overdue) "Talk to a human". *Bills and recharge* picks a biller, takes the consumer number or mobile (typed, never spoken), a listed plan for a recharge, then Review and Pay; the amount comes from the server and the guardrail checks list is shown, with an OTP box above the auto limit. *Spends* is a plain-CSS bar list for the last 30 days. *Settlements* shows a merchant's payouts and the plain cause of a failed one. Voice examples: "mera payment fail ho gaya", "bijli bill bhar do", "199 ka jio recharge", "is mahine kahan zyada kharcha hua", "mera settlement kab aayega". Voice only opens the screen and pre-selects the biller; it never auto-submits.
- **Language:** tap the avatar (top left) for Account and language. The app's fixed wording (`web/i18n/<code>.json`) and the assistant's answers (`config/consumer_kb_i18n.yaml`) are machine-translated ahead of time with Sarvam Translate by `python scripts/build_i18n.py` (needs `SARVAM_API_KEY`; re-run it after changing any UI text, then `python -m pytest tests/test_i18n.py`). Nothing the person types or sees is sent for translation; text built at run time (names, amounts, quotes) stays as the app wrote it. Wording is not native-speaker reviewed.
- Document autofill (insurance step 1) runs on the device: the photo is read by Tesseract.js in the browser tab (engine and English model load from jsDelivr, the photo is never uploaded), `docparse.js` extracts name, date of birth, gender and PAN, and an Aadhaar number is detected only to be ignored. Test the parser with `node web/docparse.test.js`.
- **Sample documents** (`web/samples/`, made by `python -m data.sample_docs`, listed in `manifest.json`): 47 invented files in 10 cases, each a short story with the verdict it must get: a clean approved claim, a renewed policy approved in full, the same claim as scans and a tilted photo, an approval letter with the amount changed, a bill in someone else's name, a claim the insurer does not know, an already-paid claim, a letter for a rejected claim, an approval the insurer has not issued, and a policy with a hospital's cost estimate (pre-approval). Every page says it is a demo with invented data. Use them to try *Read a document* and the verification.
- **Read a document** (Health Insurance, *Read a document*): choose a policy, hospital bill, discharge summary, claim acknowledgement or approval letter (PDF or photo, several files = several pages). `docread.js` reads a PDF's text layer with pdf.js, and OCRs a scanned page or a photo with Tesseract.js (both load from jsDelivr as code; the file is never uploaded). Only the text goes to `POST /api/consumer/docs/read`, which classifies it, reads every labelled value and shows where it came from (page and line), what is missing and what needs a second look. It is a reading only: nothing is saved and nothing is bought, claimed or paid because of it. `node web/docread.test.js` tests the line grouping.
- **Claim documents** (Health Insurance, *Claim documents*): add the files of a claim (one file per document, PDF or photo) or pick one of the 10 sample stories (*Try a sample claim*). Each file is read on the device; the server (`POST /api/consumer/docs/verify`) re-reads the text, cross-checks the documents with each other and the insurer's simulated record, and the screen shows the verdict, every check (does not agree / please check / could not be checked / agrees), the **estimate** of what the policy would probably pay (each deduction with its policy page), the risk signals that ask a person to look, and the payout timing outlook. Only a fully `consistent` approved claim shows *See my advance offer*, which calls `POST /bridge/from-documents` (amount and payout date come from the insurer record on the server) and then the normal advance screens (Key Facts, consents, OTP above the limit). *Before admission* gives an estimate only: financing before admission is not built yet. With `KAAMEZY_DEMO_WAIVE_WAITING=1` on the server, an in-app policy's waiting period is shown but not applied, and the screen says so.
- **What the agent did** (Health Insurance, *What the agent did*): a read-only view of the pipeline's append-only agent log (`GET /pipeline/runs`). Each run of a claim's documents shows its six stages (read, check, estimate, signals, rules, offer) with a status, a plain headline and the codes and rupee figures behind it, and the outcome (an offer was prepared, a person must look, or no offer). It never holds document text, names or reference numbers, cannot change a run and cannot start any money moving. The Claim documents result links to it.
- Loan: the lender sees only age, income and EMIs; the Key Facts Statement is shown (and timed by the server) before two separate consents; a policy holder can file a claim with a simulated insurer (My claims), and once it is approved and waiting for its payout can ask for a short advance against it (sized only from the approved claim, repaid from the payout, same Key Facts / KYC / consent / OTP steps). The personal loan itself never looks at a policy.
- Deploying: the Render backend must be redeployed with the consumer code and these env vars: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `CHAUKAS_STAFF_KEY`. Without `SUPABASE_URL` the consumer API runs in `off` mode (one shared demo user), which is only for local development.

- **Sign-in is switched off for the demo** (`NO_AUTH = true` in `index.html`; it is `false` now, so sign-in is on): the app opens straight on the home screen as one shared demo user, and the server must run with `CHAUKAS_CONSUMER_AUTH=off` (on Render set it as an environment variable). Set `NO_AUTH` to `false` and `CHAUKAS_CONSUMER_AUTH=supabase` to bring the Supabase sign-in back. With auth off, every visitor shares the same data: do not use real details.
